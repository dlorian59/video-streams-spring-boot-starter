# 0.1.0 — От загруженного файла к защищённому воспроизведению

[Версии](../index.md) · [English](en.md) · [Русский](ru.md) · [README](../../README.md)

Загрузка сохраняет файл, но видео ещё нужно подготовить для проигрывания. Разделяйте операции: обычный file-streams фиксирует единый непрерывный поток исходника, затем video-streams готовит поколение HLS VOD. После этого браузер запрашивает плейлист и отдельные сегменты вместо сборки целого исходника в Blob.

Начните с [подключения к существующему проекту](../../README.md). Эта глава разбирает решения и отказы на [полном защищённом потребителе](../../examples/secured-video). Включены Maven- и Gradle-сборки; подготовка артефактов и команды запуска находятся в [документе разработки](../../CONTRIBUTING.md).

## Что требуется

Нужны Java 17+, Boot 4.1.2 с WebFlux, принадлежащий приложению ObjectStreams (обычно S3-интеграция file-streams) и исполняемые FFmpeg/ffprobe. Core формирует один H.264/AAC fMP4 HLS VOD-вариант: вписывание в 1280×720, 30 fps и целевые сегменты около двух секунд. Это не live streaming, не адаптивный выбор качества, не DRM и не исполнитель произвольных команд FFmpeg.

Выделите процессу закрытый рабочий каталог с правом записи и подходящими квотами диска/CPU. До кодирования исходник скачивается в ограниченный локальный файл; просмотр не начинается во время загрузки исходника. В браузере нет большого source Blob, но серверу всё равно нужен временный диск. Зависимости не устанавливают FFmpeg и не открывают публичный маршрут.

<a id="storage-and-lifecycle"></a>
## Одно хранилище и явный жизненный цикл

Включите file-streams и оставьте file-streams.http.enabled=false. Профиль MEDIA согласует предел исходной загрузки с video-default 512 МиБ. video-streams.enabled=true добавляет VideoOptions, VideoStreams и — в reactive web-приложении с StreamLimits — VideoAssetHandler. Собственные beans имеют приоритет. Нужен один однозначный ObjectStreams; при нескольких выберите нужный через @Primary.

[Автоконфигурация](../../src/main/java/io/github/alex59/videostreams/boot/VideoStreamsAutoConfiguration.java) использует существующий ObjectStreams, а не создаёт второй S3-engine. При остановке Spring закрывает созданный им VideoStreams и отменяет его работу. Core не закрывает переданный ObjectStreams/client. Владельцем клиента остаётся file-streams или приложение.

Сохраните свой AWS credentials provider и конфигурацию секретов. Полный пример использует настраиваемый S3 endpoint для изолированной проверки, но не содержит учётных данных в исходниках. Права bucket и срок хранения задаёт приложение/инфраструктура. Очередь необязательна: если подготовка должна переживать HTTP-disconnect или перезапуск процесса, вызывайте тот же prepare из своей долговечной job-системы и сохраняйте результат там.

<a id="preparation"></a>
## Сначала загрузка, затем подготовка

[Контроллер](../../examples/secured-video/src/main/java/example/video/VideoController.java) показывает последовательность:

1. Аутентифицированный аккаунт выбирает новый ID исходника, например demo:training-2026. Пространство имён проверяется по настоящему Principal, не по account-header клиента.
2. PUT /api/video-sources/{encodedId} передаёт исходник через ObjectStreamHandler. Перед prepare дождитесь HTTP 201 и committed=true. Возвращённый key совпадает с ID браузера.
3. POST /api/videos/{encodedId}/prepare отправляет {"sourceKey":"demo:training-2026"}. Тело должно совпасть с маршрутом, а маршрут пройти авторизацию до вызова VideoStreams.
4. [Сервис](../../examples/secured-video/src/main/java/example/video/VideoService.java) возвращает videos.prepare(sourceKey), преобразуя только публичный результат. Подписка принадлежит WebFlux: не нужны ручные subscribe, block, executor или аннотация планировщика.
5. Успешный HTTP 201 содержит status=ready, UUID generation, относительный playlistUrl, durationSeconds и segmentCount. Сохраните результат в доменной модели, если он должен пережить перезагрузку страницы. Пример возвращает его напрямую и не создаёт скрытый каталог.

Core проверяет подготовленные файлы и сохраняет init/медиа до публикации playlist.m3u8. Поэтому ready описывает завершённое поколение. Каждый prepare — новая операция с новым поколением; повтор не является дедуплицированным retry. Синхронный запрос удобен для умеренных роликов, но требует согласованных тайм-аутов reverse proxy. Для долгих задач повторами, идемпотентностью и метаданными результата должна явно владеть долговечная очередь.

### Изменения и версии исходника

Для каждого исходника используйте новый неизменяемый ID либо версионированные метаданные. Пример проверяет владельца, но не реализует реестр write-once исходников. Повторная загрузка под тем же ID меняет вход будущего prepare. Параллельная перезапись — гонка приложения: стартер не может угадать нужную бизнес-версию. Уже подготовленные поколения остаются отдельными неизменяемыми результатами.

Отмена запроса по возможности останавливает подписанную работу. Отмена при публикации плейлиста может совпасть с успешным commit хранилища. Поэтому потерянный HTTP-ответ иногда означает готовое поколение, метаданные которого клиент не получил. Не показывайте автоматический откат и не повторяйте prepare автоматически.

<a id="playback"></a>
## Проверка доступа к каждому запросу

URL результата имеет вид /api/videos/{encodedId}/assets/{generation}/playlist.m3u8. Плейлист содержит относительные init.mp4 и segment-NNNNNN.m4s: они наследуют тот же защищённый маршрут и поколение.

[VideoController.asset](../../examples/secured-video/src/main/java/example/video/VideoController.java) проверяет владельца каждого запроса до делегирования VideoAssetHandler. Handler разрешает только допустимые имена артефактов и переиспользует streaming/range из file-streams. UUID не предоставляет доступ. Правило примера позволяет аккаунту читать все поколения своего исходника; добавьте доменные ACL/отзыв прав, если этого недостаточно.

Общий /objects/** не включён. Второй маршрут к физическим ключам мог бы обойти авторизацию медиа-контроллера. Не помещайте bearer credentials в URL плейлиста. Настройте TLS и private/authenticated cache-политику в приложении: общий кэш ответа между аккаунтами не является функцией стартера.

<a id="browser-flow"></a>
## Связь загрузки и просмотра

[video-streams-react](https://github.com/dlorian59/video-streams-react) использует файловый компонент и отдельный prepare URL. Задайте objectsUrl=/api/video-sources, objectKey=demo:&lt;новый-id&gt; и prepareUrl=/api/videos/{encodedId}/prepare. playlistUrl результата передаётся HLS-плееру; UI приложения не пересобирает URL и не скачивает исходник в Blob.

Используйте один same-origin transport с аутентификацией для загрузки, подготовки, плейлиста и сегментов. [DemoSecurity](../../examples/secured-video/src/main/java/example/video/DemoSecurity.java) нужен полному примеру только для самостоятельного запуска. Существующее приложение сохраняет свою security-систему.

Вход в примере: GET /api/session → POST /login form-urlencoded с username/password и полученным CSRF-header → повторный GET /api/session. Ответ содержит username, csrfHeader и csrfToken. Аутентификация хранится в HttpOnly secure cookie сессии и передаётся браузером автоматически. Актуальный CSRF-header нужен для небезопасных upload/prepare-запросов. Защищённые GET тоже требуют cookie. CSRF-токен не заменяет аутентификацию.

Frontend демо может проксировать /api на TLS/HTTP2 backend, сохраняя same-origin. Потоковое тело запроса требует поддержки браузера/протокола; файловый компонент сообщает о неподдерживаемом режиме вместо полной буферизации исходника. V1 использует MSE/hls.js и сообщает о неподдерживаемом просмотре, если engine недоступен. Native HLS не входит в эту версию: ему нужна отдельная интеграция приложения и совместимая аутентификация. [Исполняемый React-пример](https://github.com/dlorian59/video-streams-react/tree/main/examples).

<a id="failures"></a>
## Ограничения работы и отказы

Defaults: три минуты на всю подготовку, 512 МиБ входа и выхода, 300 медиасегментов и две параллельные подготовки. При ограниченном CPU/диске уменьшите max-concurrent. Согласуйте лимиты исходной загрузки, передачи объектов и подготовки: сохранённый исходник ещё не обещает успешно подготовленное видео. [Все настройки](reference.ru.md).

- INVALID_SOURCE/400: неподходящий исходник или структура медиа. Исправьте вход; повтор того же некорректного файла не помогает.
- TOO_LARGE/413: превышен один из лимитов. Выберите подходящие ресурсы/пределы или меньший вход, не обрезайте видео молча.
- BUSY/429: заняты активные слоты подготовки. Решение о новой операции принимает клиент; скрытой очереди ожидания нет.
- PROCESS_FAILED/502: проверьте серверную диагностику и доступность executable. Не выдавайте клиенту локальные пути/сырой вывод FFmpeg.
- TIMEOUT/504, STORAGE_FAILED/502 или disconnect: результат мог сохраниться без подтверждения. Пример сообщает неизвестный исход, не откат.
- CLOSED/CANCELLED/503: сервис закрывается или работа отменена. Повтор — новая подготовка, не продолжение.

[Адаптер ошибок](../../examples/secured-video/src/main/java/example/video/VideoErrors.java) раскрывает категории без сырой диагностики. Лимиты core и завершение процессов снижают утечки ресурсов, но не заменяют изоляцию CPU/диска. У ObjectStreams нет удаления: неудачная подготовка может оставить несвязанные неизменяемые артефакты. Настройте retention/очистку отдельно; не удаляйте потенциально сохранённый плейлист только из-за потерянного ответа.

## Что нужно знать

Commit исходника, готовность видео и просмотр — разные состояния. Одна граница хранилища обслуживает файлы и артефакты видео. Проверка доступа принадлежит приложению и выполняется на каждом запросе. Поколение делает результат неизменяемым, но не даёт exactly-once подготовки. Defaults сокращают lifecycle-код; лимиты, credentials, авторизация и политика долговечных задач остаются решениями приложения.

[CSRF в Spring Security](https://docs.spring.io/spring-security/reference/reactive/exploits/csrf.html) объясняет сессии и токены примера. [HTTP/2 Spring Boot](https://docs.spring.io/spring-boot/how-to/webserver.html#howto.webserver.configure-http2) описывает TLS/HTTP2-конфигурацию.
